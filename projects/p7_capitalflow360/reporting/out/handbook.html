1. Scope, honesty and contribution

What CapitalFlow 360 is

CapitalFlow 360 is an independent portfolio project. It simulates how a bank's operations platform carries trades in six asset classes from order to settled cash and reconciled books: orders and fills, booking, allocation, confirmation matching, clearing, settlement, a double-entry ledger, reconciliation against custodian statements, and exceptions. It has seven role workspaces, seven dashboards, a Bronze/Silver/Gold lakehouse, and a test system that generates and executes thousands of cases against an independent oracle.

What it is not

  • It is not connected to any real exchange, broker, clearing house, custodian, payment system or messaging network. Venues and counterparties are simulators driven by synthetic files.
  • All data is synthetic, generated from a fixed seed. No client, trade or price is real.
  • Calculations follow standard market conventions (day counts, spot dates, VWAP, accrued interest) but it is not production-grade pricing, and it makes no claim of regulatory compliance.
  • {f"A public demo runs on free tiers ({DEP['host_short']}) at {DEP['url']}, checked from GitHub Actions on {DEP['deployed_on']}" if DEP else "It has not been deployed publicly at the time of writing"}, and the Databricks notebook has not yet been executed on Databricks. The lakehouse ran on local Spark and Delta Lake.

Request path

A booking arrives at POST /api/trades with an Idempotency-Key. Pydantic validates the shape; the rules engine enriches and checks the trade (eligibility, calendar, economics, limits); the service writes the trade, its allocations, lifecycle event, and audit event in one transaction with the request's correlation id. Downstream stages are driven by the simulators and the end-of-day processor, and every state change goes through the server-side state machine. The React screens only ever call the API.

Decisions worth explaining

  • Decimal everywhere. Money and quantities are Python Decimal and PostgreSQL NUMERIC, rounded half-up to each currency's minor unit (JPY has none). Floats never touch an amount.
  • Idempotency at two levels. The API honours Idempotency-Key (same key and body returns the first result; a different body is refused with 409), and every ledger posting carries a unique event key so replaying a day posts nothing twice.
  • Optimistic concurrency. Amendments send If-Match with the version they read. A stale version is refused, so two users cannot silently overwrite each other.
  • Server-side state machine. Each product family has its own allowed edges. An illegal move returns 409 even if someone calls the API directly.
  • One error envelope. Every error returns a code, message, details and the correlation id, so a support analyst can find the audit trail.
  • Append-only audit. A database trigger refuses UPDATE and DELETE on audit events.
  • Sandboxes for tests. Lifecycle tests run in sandboxes tagged on every row, and dry-run bookings sit inside savepoints that roll back, so tests never disturb the main book.
  • Defects as switches. Six realistic defects are compiled in but off by default; CF360_DEFECTS turns one on, which is how the tests are proven able to fail.

Every trade walks the same spine and stops where its product stops. The edges are written out by hand in testkit/oracle/specs.py and tested both ways: every allowed edge must succeed and every other edge must be refused.

Side states

Partially settled, settlement failed, pending approval, amended (a new version), cancelled and exception. A settled trade cannot be amended economically; it is cancelled with exact reversing ledger entries and rebooked.

Reading the status mix

Most cash products have settled. Derivatives and financing trades sit in Open by design: they live until expiry, maturity or close. The handful of failed and partially settled trades are the planted fails, each with an exception routed to settlements.

  • Economic changes (quantity, price, dates, account) need a checker. Non-economic changes (book, trader) apply directly as a new version.

Audit trail

Every request carries a correlation id, returned in the response header and the error envelope and stored on every audit event it causes. The audit table is append-only at the database level. At the statement date it holds 3,702 events.

10. Lakehouse: Bronze, Silver, Gold

ExcelParquet landingBronze (stream)Silver (gate, MERGE)Gold
  • Landing converts each sheet to Parquet with every value kept as text, and checks columns against the contract. A sheet whose columns drift is refused whole (DQ05) rather than half-loaded.
  • Bronze appends with a streaming checkpoint, so re-running ingests only new files.
  • Silver casts types, checks required fields, references and domains, de-duplicates, quarantines bad rows with the rule that caught them, then MERGEs, but only if less than 5% of the batch was quarantined.
  • Gold builds the trade lifecycle (500 rows), a cash position projection (293 rows) and a data-quality summary.

11. Test strategy

The rule: expected results never come from the code under test. They come from four independent places:

  1. An independent oracle in testkit/oracle, written with exact fractions, recomputes economics, dates and outcomes. An import test proves it shares no code with the platform.
  2. Documented rule boundaries in the catalogue: for example a price 10.00% from reference is accepted and 10.01% is rejected.
  3. Hand-written specifications: lifecycle edges per product family and the role permission matrix.
  4. Hand-calculated worked examples (section 8).

17. Interview questions and answers

63 questions, grouped by theme. Answer in your own words; the point is to know the substance, not to recite.

Scope

Q1What is CapitalFlow 360 in one sentence?
A simulated multi-asset operations platform that carries 500 synthetic trades from order to reconciled books, with a test system that proves its results against an independent oracle.
Q2Is it connected to real markets?
No. Venues, the CCP, custodians and counterparties are simulators fed from synthetic files. It makes no claim of production pricing or regulatory compliance.
Q3What did you do and what did the AI do?
I set the scope, lifecycle, rules and their boundaries, the roles and controls, the scenarios, negative data types and the defect plan, and I reviewed results. The code was written with an AI coding assistant, and every result was run and checked.
Q4Why six asset classes?
They have genuinely different lifecycles: cash products settle DVP, FX needs two calendars, futures settle margin, options exercise, swaps pay schedules and financing has two legs. Fewer would hide the hard parts.
Q5Why exactly 500 trades?
Enough to exercise every path and planted exception, small enough to reason about every one. The split is fixed: 140 equities and ETFs, 120 bonds, 80 FX, 70 listed derivatives, 50 swaps, 40 financing.
Q6Is it deployed?
Not publicly yet. It runs with Docker Compose, and a free Vercel plus Neon setup is documented; nothing that can charge is switched on without approval.

Business process

Q7Walk me through a trade's life.
Order and fills, booking at the volume-weighted price, allocation to accounts, confirmation matching, clearing where a CCP applies, settlement instruction from the SSI, settlement, ledger posting, reconciliation.
Q8How is the booked price set when an order fills in clips?
Volume-weighted average of the fills to six decimals. For 600 at 71.00 and 300 at 71.10 it is 71.033333. Rule R026 rejects a booking that disagrees with its fills.
Q9How are allocations rounded?
Pro-rata quantities must sum to the block (R024). Amounts are rounded to the currency's minor unit and the residual goes to the largest allocation, first on ties (R025).
Q10How do you derive an FX spot date?
T+2 business days, and the date must be a business day on both currencies' calendars. Defect D3 checks only the base-currency calendar and 46 cases fail.
Q11What is an SSI and why is it effective-dated?
Standing settlement instructions tell you where to deliver. They change over time, so the one valid on the settlement date is used. An SSI that ended the day before counts as missing (R080).
Q12What happens on a settlement fail?
The instruction is marked failed with a reason, an exception goes to settlements, it ages by business days, and it retries. Partial settlement needs at least one lot available (R085).
Q13What does reconciliation compare?
Internal positions and cash from the ledger against custodian statements, per account and instrument or currency. Differences above tolerance become breaks.
Q14What is your cash tolerance?
A difference of 0.50 or less is inside tolerance (R096) and is not a break; anything larger is.
Q15How do futures differ in settlement?
They do not deliver notional; they settle daily variation margin against the settlement price, and initial margin is held. They stay Open until expiry or close.
Q16How are repos handled?
Two legs: opening cash against collateral with a haircut, and closing cash with interest. Collateral value is checked and margin calls raised when it falls short.
Q17What is maker-checker here?
Economic changes need a second person. The maker requests, a checker approves, the trade gets a new version and allocations are re-cut. A maker cannot approve their own request.
Q18Can you amend a settled trade?
Not economically. You cancel it, which posts exact reversing ledger entries, and rebook (R090).
Q19How are exceptions routed?
Each exception type has an owning team: matching breaks to middle office, fails to settlements, breaks to reconciliation, margin calls to risk. Each has an age and a status.
Q20What is a potential duplicate?
A booking with the same economics as another but a different source reference (R029). It is flagged as a warning for review, not rejected, because genuine repeats happen.

Rules and calculations

Q21How many rules are there and how are they organised?
69 rules in 18 families such as eligibility, calendar, economics, settlement and data quality. Each has an id, an error code and documented boundaries.
Q22Give an example of a boundary.
The price collar: 10.00% away from the reference price is accepted, 10.01% is rejected. Cases are generated on both sides.
Q23How do you compute bond accrued interest?
Coupon times the day-count fraction from the last coupon date to settlement. 30/360 for US corporates, ACT/ACT for Treasuries and gilts. Defect D2 used ACT/360 for 30/360 bonds and 52 cases failed.
Q24What is an ex-dividend period?
For gilts, trades settling in the last days before a coupon do not receive it, so accrued interest is negative. Worked example WE11 shows it.
Q25How do you handle JPY?
It has no minor unit, so amounts round to whole yen. Worked example WE05 checks it.
Q26How do you avoid rounding errors?
Decimal arithmetic end to end, half-up rounding to minor units at defined points, and an oracle using exact fractions to compare against.
Q27How are commissions computed?
Basis points on gross consideration with a minimum per trade, plus exchange fees, and UK stamp duty on purchases only.
Q28What is in a hand-calculated worked example?
Inputs, the working, and the expected value, written by hand. There are 28, and each must match both the platform and the oracle.

Architecture and engineering

Q29Why FastAPI and PostgreSQL?
FastAPI gives typed request validation and an OpenAPI contract for free; PostgreSQL gives NUMERIC, transactions, constraints and triggers that suit a ledger.
Q30How do you make bookings idempotent?
Clients send an Idempotency-Key. The same key and body returns the first result; the same key with a different body is refused with 409.
Q31And the ledger?
Each posting has a unique event key per leg, so replaying a settlement batch posts nothing new. Defect D5 bypasses it and the idempotency check fails.
Q32How do you stop two users overwriting each other?
Optimistic concurrency: amendments send If-Match with the version read; a stale version is refused (R098).
Q33Where is the state machine enforced?
On the server. Each product family has allowed edges; any other move returns 409, whoever calls it.
Q34How is the audit trail tamper-evident?
A database trigger refuses UPDATE and DELETE on audit events, and every event carries the request's correlation id.
Q35How do tests run without polluting data?
Lifecycle tests run in sandboxes tagged on every row; dry-run bookings run inside savepoints that roll back; each full run starts from a fresh seed.
Q36How are schema changes managed?
Alembic migrations, three revisions so far, used to build every database including the test one.
Q37How do the dashboards stay consistent?
One metrics service computes every KPI with its definition, numerator, denominator and population; all screens and these reports read from it.
Q38How would you scale it?
Move end-of-day processing to a job queue, partition ledger and events by business date, and put read models behind the dashboards. Current timings are single-machine, not load tests.

Data and lakehouse

Q39How is the synthetic data generated?
Python with a fixed seed (20261116), written to Excel with openpyxl, with a manifest of hashes and row counts so any change is visible.
Q40Why keep negative data separate?
So the baseline stays clean and every bad row is labelled with the rule, error and layer that should catch it.
Q41What does Bronze, Silver, Gold mean here?
Bronze is raw appended data, Silver is typed, validated and de-duplicated with bad rows quarantined, Gold is business tables: lifecycle, cash projection, data-quality summary.
Q42What is the quality gate?
If more than 5% of a batch is quarantined, Silver does not MERGE it. The negative batch quarantined 17% and was held back.
Q43How do you handle schema drift?
Landing compares columns to a contract generated from the dictionary sheets. A drifted sheet is refused whole (DQ05) rather than half-loaded.
Q44How do you prove MERGE is idempotent?
Re-running the same batch ingests 0 Bronze rows and inserts or updates 0 Silver rows; a full rebuild from landing reproduces Silver's hash.
Q45Did it run on Databricks?
Not yet. It ran on local Spark and Delta Lake with 14 of 14 checks passing. The notebook and serverless job are written for Databricks and need a workspace run.
Q46How does the lakehouse tie back to the platform?
Silver trades are compared to both the oracle and the platform database: same ids, quantities, prices and settlement dates.

Testing

Q47How do your tests know the right answer?
Expected results come from an independent oracle, documented boundaries, hand-written specs and hand calculations; never from the code under test.
Q48How many tests are there?
2,370 generated cases in 137 scenarios. The clean run executed all of them, 2,410 executions including browser runs, with 0 failures.
Q49How do you know the tests can fail?
Six realistic defects were injected one at a time; every one was caught, from 1 to 52 failing cases each, then a clean rerun passed.
Q50Which defect was hardest to catch?
D5, the ledger idempotency bypass. Only one targeted check catches it, so that check had to be designed deliberately.
Q51What did the tests find that you did not plant?
Five real issues, including allocation checks built as warnings (a 600-share allocation of 500 was accepted) and authorisation running after validation.
Q52What is the role matrix?
Every protected endpoint called as every role, with an expected allow or 403. 264 cases.
Q53How do browser tests map to cases?
Each Playwright title starts with its catalogue id, so results merge back to the case, scenario and rules.
Q54Which browsers?
Chromium, Firefox and WebKit, desktop plus phone-sized Chromium and WebKit: 245 runs in GitHub Actions run CI-3, 0 failed. Locally only Chromium could be installed.
Q55What is your rule coverage?
64 of 69 rules have executed cases. The remaining ones are listed openly as gaps.
Q56How do you avoid flaky tests?
Fresh seeds per run, a fixed business clock, server-side waits on visible state rather than sleeps, and sandboxes for anything that writes.
Q57How is traceability recorded?
Every case names its rules, scenario and source row or spec; a traceability workbook links rules to cases and results.

Behavioural and judgement

Q58What was the hardest design decision?
Where to put the boundary between platform and oracle. If they share code, the tests prove nothing, so the oracle uses exact fractions and an import test proves independence.
Q59What would you do differently?
Write the negative data labels first. They found the most serious bug, and earlier labels would have found it sooner.
Q60How did you use AI responsibly?
I specified the behaviour and the expected results; the AI wrote code; nothing was accepted until it passed cases whose answers came from elsewhere. Failures were reported, not hidden.
Q61How does your banking background show in this?
The planted exceptions, the SSI and calendar rules, maker-checker, and reconciliation tolerances are what operations teams deal with daily. I chose them because they break in real life.
Q62What would you build next?
A Databricks run of the same checks, cases for the uncovered rules, and a small assistant that explains an exception using its audit trail.
Q63How would you explain this to a non-technical stakeholder?
It is a practice trading floor's back office on fake data, plus an automatic checker that knows the right answers and proves the system gets them.
