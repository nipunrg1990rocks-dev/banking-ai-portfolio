Ledgerline Risk Control Room

A risk and data-quality dashboard for a bank that does more than show red tiles. An AI agent investigates every metric each morning. It finds which desk or feed moved the number, links the move to the change that caused it, forecasts when a limit will break and drafts the actions the risk appetite policy requires. A named risk owner approves the board pack.

The AI layer

The agent works a red tile like an analyst

Open reconciliation breaks · 56 · limit 45Root cause: high confidence
  1. 1Scan all 20 metrics and rank what moved. Breaks went from 33 to 56 in a week. scan_metrics
  2. 2Break the change down by reconciliation: the EUR nostro accounts for +28. explain_change
  3. 3Find when it started: a step change on 6 October. find_onset
  4. 4Check the change log: core banking release R26.10 went live on 5 October and feeds that reconciliation. correlate_changes
  5. 5Forecast and act: a level shift that won't self-correct, so the 32 items are assigned to an owner with a due date under RAS-004. forecast get_policy
Ask it anything

"Why did reconciliation breaks go up?" "What if another USD 300m of deposits leaves?" "When will the AML KRI breach?" Answers cite the metric, the SQL and the tool calls behind them.

The free hosted demo runs the agent offline, a fixed playbook that uses the same tools without an LLM. Live mode uses Databricks' free foundation models in a Databricks workspace (or Claude). If the model states a number no tool returned, the answer is rejected and the offline answer is shown.

The banking problem

Dashboards say what is red, not why

A risk committee pack shows a breached KRI. Then analysts spend days asking which desk, which feed, since when, and what changed. By the time the answer arrives the next pack is due. Data-quality problems make it worse: a late feed quietly turns a KRI green. This control room puts the investigation next to the number and treats data quality as a risk in its own right.

The agent was replayed as if it were each business day from 3 August to 9 October, seeing only the data up to that day. The synthetic history has seven planted incidents and several harmless changes as decoys. These checks confirm the design works as intended; they are not an independent benchmark.

Controls built in

What a reviewer would expect

  • Every metric has an owner, thresholds, a policy reference and visible SQL
  • Root causes are hypotheses with a confidence level, never stated as fact
  • LLM answers must be grounded in tool results or they are not shown
  • The board pack needs a named approver and is fingerprinted with SHA-256
  • Every agent step and approval is in a hash-chained audit log
  • Each page says what is real and what is simulated
